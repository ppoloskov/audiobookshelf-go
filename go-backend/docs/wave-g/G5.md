## Entrypoint coverage / negative space

- Identity surface in tracked Go is `identity.Handler.Handle` and userapi route dispatch; the named auth transitions are login, `/auth/refresh`, logout, user profile patch/delete, and API-key CRUD. The current `identity/routes.go` public route registrar is untracked owner WIP and deliberately not treated as shipping code.
- Sharing public endpoints are wired through `sharing.Handler` (`sharing/handler.go`); primary public transitions are share resolve/session creation, progress, cover, track, download, create, delete, and feeds. `findShare` vs `loadShare` is the salient negative-space distinction: lookup-only routes bypass active expiry cleanup.
- No persisted socket-session table exists: socket auth is a one-time event; revocation is the hub refresh/disconnect path. No user/profile mutation emits `user_updated` to the changed user; current Go emits to actor (`userapi/userapi.go:674-678`), matching the targeted TS actor event (`UserController.js:346-348`).
- Delete user leaves API-key rows pointing to the missing owner unless schema FK behavior removes them; authentication rejects because `apiKeyUser` resolves owner and rejects missing user (`identity/identity.go:916-919`). This is safe denial, but row cleanup/response projection should be checked before claiming cascade parity.
- Tests found: `identity/revocation_test.go` covers expired/inactive refresh rejection and expired-row cleanup; `identity/identity_test.go` covers login/refresh rotation grace, API-key auth and one-time init, current-session preservation and invalid-current fallback; `realtime/hub_test.go` covers permission refresh and deleted-user disconnect; `sharing/handler_test.go` is present. No independent test was found in the inspected output that directly proves expired share cover/track revocation or API-key revocation of an already-authenticated socket.

The earlier `findShare` vs `loadShare` distinction was not mapped to those route callers. Do not add the proposed expiry fix; only retain coverage for that shared guard if later tests show an uncovered caller.
2. **Credential/profile update partial commit before refresh-session invalidation** — medium severity, source-observed (pending independent reproduction) ordering; failure-injection needed to characterize stale-token window.
3. **Already-connected socket after API-key-only revocation/owner change** — medium-low, hypothesis pending pinned-TS comparison; do not alter without evidence because socket is authenticated once on both sides.
4. **Immediate-expiry share event order and ignored cleanup errors** — medium-low, concrete difference candidate; check event sequence and retry behavior.
5. **Fractional API-key TTL representation boundary** — low, source-observed (pending independent reproduction) small rounding difference, likely TS-compatible.
