## Ranked suspects

1. **Item DELETE feed event missing (source-observed (pending independent reproduction), high).** `item_delete.go:126-128` performs raw feed-row deletion; TS `ApiRouter.js:387-388` calls close manager; `RssFeedManager.js:355-377` emits `rss_feed_closed`. Both callers of `deleteItemRows` (single delete and whole-library delete) inherit the missing event. Tests should lock row removal, event payload and event order. Do not reuse `itemwrite.closeFeeds` inside the transaction: it queries/deletes through the pool and emits outside transactional state; a correct fix must preserve event payload while respecting commit/failure ordering.
2. **Whole-library DELETE bypasses per-item dependent side effects (source-observed (pending independent reproduction) feed row/event gap; high).** `library_writes.go:435` uses `deleteItemRows` and `:475+` emits only library/item/playlist events. TS library controller routes every item through shared delete helper. Cover cache purge also appears absent.
3. **Item and library delete omit cover cache purge (strong hypothesis, medium-high).** TS helper calls purge (`ApiRouter.js` after feed close); Go's item and bulk deletion have no observed `purgeCoverCache` call. Validate whether cache keys remain externally observable after DB row disappears; test cache state directly.
4. **Bulk item deletion filesystem parity (source-observed (pending independent reproduction) limitation of hard semantics, lower priority).** Single delete handles hard file removal (`item_delete.go:74-76`), bulk library deletion only removes metadata item dirs (`library_writes.go:484-490`). TS library delete likely handles each underlying item path; verify `LibraryController.js:525-590` before labeling a bug, since library deletion may intentionally preserve media files.
5. **Author delete partial-failure semantics / image cache details (hypothesis, medium-low).** Go deletes entity before metadata writes and can return error after irreversible delete; TS also destroys before sequential saves. Need explicit fault-injection parity check, not inferred as a bug.

## Proposed minimal regression

Add endpoint lifecycle regressions for both callers. Single item: seed item feed plus a series feed and linked author/series; invoke `DELETE /api/items/{id}`. TS order is item-feed `rss_feed_closed` before `item_removed`, followed by orphan `series_removed`, then series-feed `rss_feed_closed`; Go currently emits `item_removed` before the sweep and has no item-feed close event. Assert row state and recipient/payload/event order. Whole-library: two item feeds; assert each is closed (event emitted) and cache purged before `library_removed`, preserving TS sequential helper behavior. A fix should collect feed summaries in transaction, commit, then emit (and must define behavior if commit fails); do not call pool-based `itemwrite.closeFeeds` from an open transaction.
