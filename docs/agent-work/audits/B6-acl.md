# B6 — ACL and permission characterization (v2.37.2)

Read-only source audit against upstream baseline `edb1f7efc92ecacdef51aafb4d9d5054ce10604` (v2.37.2). No runtime tests were executed as part of this source characterization. Line references are repository-relative and refer to the pinned checkout.

## Source semantics

- Library authorization is `accessAllLibraries || librariesAccessible.includes(id)` (`server/models/User.js:646-650`). Admin/root operation gates are separate, not the library ACL.
- Item tag rule (`server/models/User.js:658-666`): accessAllTags grants. Denylist mode allows untagged items and otherwise requires **every** item tag absent from selected tags. Allowlist mode requires nonempty tags and **some** overlap with selected tags. Full item check also requires library access and explicit-content permission (`User.js:675-683`).
- Query/list tag filtering (`server/utils/queries/libraryItemsBookFilters.js:17-42`, podcast equivalent `server/utils/queries/libraryItemsPodcastFilters.js:17-39`, `server/utils/queries/libraryFilters.js:242-258`) adds a tag restriction only when `itemTagsSelected.length > 0`; denylist means no intersection, allowlist means at least one intersection. Explicit restriction is separate. Therefore list SQL and direct item authorization are intentionally different for empty selections.
- Controllers use the common item rule, including `LibraryItemController.js:50`, `PodcastController.js:569`, `EmailController.js:115`, `ToolsController.js:127,170`, and `MeController.js:140,195,334,367,405`.

## Divergences, risk, and existing evidence

Confirmed direct item-rule divergences: **1** — email allowlist “every” versus upstream “any”. This is the top-ranked risk: email item delivery false-denies mixed-tag items that share at least one permitted tag. Affects email item-access/send flow (`EmailController.js:115`, Go flow `internal/emailapi/handler.go:216-227`).

Potential, unconfirmed risk: podcast explicit-content gate is absent from `canAccessPodcast`; establish whether endpoint call chain enforces it before counting it as a real divergence. Admin/root shortcuts in adminops, audiotools, emailapi are role-gate composition differences; do not treat as ordinary ACL equivalence without endpoint authorization context.

The claim that the Go any-tag variant differs from both upstream semantics is not supported for item authorization by v2.37.2 `User.js`: it is the same any-tag rule. Difference exists only if mistakenly comparing item checks to upstream query/list behavior with an empty selected list. Keep those surfaces separate.

The packet’s proposed `server/utils/permissions.js`, `server/utils/libraryItemFilters.js`, and `server/controllers/SharingController.js` paths are absent in this checkout. Evidence is instead in `server/models/User.js`, `server/utils/queries/*Filters.js` and controller call sites above.

Existing differential evidence: `contracts/parity/differential-cases.json:11` defines `libraries-restricted-user`; `tools/parity/differential.cjs:36` expects 200. It verifies restricted library list response, not tag ACL. Collection/playlist parity cases are `differential.cjs:45-52`; upstream routes use library predicates (`CollectionController.js:44,116,439`; `PlaylistController.js:40,140,516,585`), and do not establish item-tag behavior. Capability `cap-route-r018.json:24` cites the restricted-user differential pass; `cap-sub-downloads.json:41` captures download permission behavior, not ACL equivalence. No capability located that fully characterizes tag ACL semantics.

## Unification decision and minimal safe changes

- **May share:** ordinary library ACL `accessAllLibraries || membership` across sharing, catalog, userapi, playback, email, and non-admin branches of other handlers. Keep root/admin and operation gates outside this helper.
- **May share after correction:** full item ACL (library + explicit + item tags) across playback, podcasts, userapi and email. Correct email allowlist to any-overlap; confirm podcast explicit enforcement at endpoint call sites.
- **Must remain distinct:** catalog/query SQL tag predicate, which activates only for nonempty selected tags, versus direct item authorization; library-list projection (`userCanListLibrary`) versus single-library authorization; administrative operation authorization versus library membership.
- Minimal implementation proposal (not performed): fix email any-tag condition; test podcast explicit call chain; consolidate only common ordinary-library and full-item predicates where endpoint gates remain intact. No broad mechanical replacement.

Required verification: (1) Go tag-matrix unit tests for allow/deny, all-tags, empty item tags, empty selection, single/multiple tags and partial overlaps, including the witness above; (2) isolated-fixture Node-vs-Go HTTP differential tests for email mixed-tag access and explicit podcast access across restricted and admin/root users; (3) separate catalog/list differential cases for empty and nonempty selected lists; (4) retain `libraries-restricted-user`, and test collection/playlist access with empty/nonempty allowed-library lists and accessAllLibraries toggled; (5) test malformed/missing permission JSON and role/operation gates separately. Compare response visibility/status, not helper return values alone.

## Conclusion

**Real confirmed divergences: 1.** **Top risk:** emailapi’s all-tags-required allowlist denies mixed-tag items that upstream permits when any one tag is selected. Podcast explicit handling remains a call-chain verification item, not a confirmed divergence. No confirmed divergence in the ordinary library ACL or catalog query predicate.
